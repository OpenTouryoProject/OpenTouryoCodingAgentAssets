# テスト先行・テスト6（司令役の手順）
対象の仕様（例 [受注一覧 OrdTf](../spec/test6-testfirst-OrdTf.md)）を、テスト仕様 → Red → Green で実装する（`TESTING.md`）。
**このファイルは司令役が読む。** 司令役は、実装役とレビュー役をサブ エージェントとして回し、人には仕様の決定だけを上げる。

## ケース1：MVC_Sample
MVC_Sample に opentouryo-* スキルを使用して実装する。

## ケース2：MVC_Sample_Core
MVC_Sample_Core に opentouryo-* スキルを使用して実装する。

## ケース3：WebForms_Sample
WebForms_Sample に opentouryo-* スキルを使用して実装する。

## 役と渡すもの
| 役 | 何者 | 渡すもの |
| --- | --- | --- |
| 司令役 | このセッション | — |
| 実装役 | サブ エージェント `opentouryo-test-implementer` | 段、ケース（フレームワーク）、[共通の決まり](../spec/test6-testfirst.md)・対象の仕様・[フレームワーク毎の共通仕様](../spec/test1-framework.md)のパス、仕様のリポジトリの場所と版 |
| レビュー役 | サブ エージェント `opentouryo-test-reviewer` | **定義の「受け取るもの」の型だけ**：段、ケース、成果物のパス（段 4 は Red のコミットも）、仕様のリポジトリの場所と版、**観点 [test6-testfirst-review.md](./test6-testfirst-review.md)**（実装役には渡さない）、実装役の報告（**セルフレビューの欄を除く**）。司令役の見立て・説明は足さない |

実装役・レビュー役は、それぞれ最初に 1 回だけ起動し、以後は `SendMessage` で同じ文脈のまま続けさせる。
途中で止まったら（使用量の上限など）、新しく起動し直さず、同じエージェントを `SendMessage` で止まったところから再開させる
（起動し直すと差し戻しの経緯を失う）。再開の指示には「最初に作業ツリーの状態（`git status`・壊す確かめの途中で退避したファイル）を確かめる」を添える。
2 人に同時にテストを流させない（DB を取り合う）。

## 手順
1. **段 0・段 1**：実装役に、テスト仕様を書かせる。報告を受けたらレビュー役に渡す。
2. **レビューの往復**：差し戻しは、レビュー役の指摘（直し方の文）をそのまま実装役に返し、直した報告を再びレビュー役に渡す。
   **司令役は成果物を直さない**（コメント・文書だけの低い指摘でも、実装役に返す。司令役が直すと、レビューを通っていない変更がコミットに入る）。
   **3 往復で承認されなければ**、論点を短くまとめて人に上げる。
   - 承認でも、レビュー役の「見ていない範囲」に差分のファイルや根拠の ID が残っていたら、そのレビューは終わっていない。残りを指定して回し直す。
   - 各段の承認の後、**レビュー役でだけ見つかった指摘**（実装役のセルフレビューに無かったもの）を数え、段ごとに記録する（終わりの報告に書く）。
3. **仕様の決定**：承認されたテスト仕様に仕様の決定（レビュー役が分類を確かめたもの）があれば、決定のレポートを書き、**人に判断を聞いて、答えが出るまで止まる**。
   - レポートは、会話や作業のファイルを知らない人が読める形にする。画面・イベントの単位で、1 件ごとに
     仕様の ID・問い・選択肢（間引かない）・推奨と理由・影響するケース・記録先と、「判断」の欄。
     - 番号は、レポートに載せた順に 1 から振る（後から足した決定は続きの番号）。
     - 記録先は 1 件ごとに書く：仕様の決定記録（`LLD/Decisions`）か、プロジェクトの規約（`test1-framework.md` など。仕様ではなく、
       このプロジェクトの作り方の決まりとの食い違い）か。
   - **判断は対話で聞く**：レポートのパスを示したうえで、1 件ずつ質問の道具（Claude Code の `AskUserQuestion`）で選択肢を示して聞く
     （推奨を先頭に。問いが複数ならそれぞれ。文言などは自由入力で聞く）。答えは司令役がレポートの「判断」の欄に書き込む。
     質問の道具が無い・人がレポートに書き込むと言ったときは、欄に `GO (b)` のように記号で書いてもらい、書き漏れ（記号・文言）を司令役が確かめて聞き直す。
   - GO：テスト仕様に決まったことを書き、段 2 へ進む。規約の決定は、根拠を「決定 N」のまま残す。
     記録先が `LLD/Decisions` の決定は、**司令役が仕様のリポジトリのクローンに記録の案を書く**（その `LLD/Decisions.md` の「記載項目」に従い、
     番号は続きから。人の判断に無いことを書き足さない。ワーキング ツリーまでで、コミットは人）。クローンの場所が分からなければ人に聞く（推測で探さない）。
     人が「記録をコミットした」と言ったら、司令役がその版の差分（決定記録だけか）を確かめ、下の「仕様の更新」で根拠を `DEC-*` に置き換える。
   - NOGO：人が仕様を直すのを待ち、下の「仕様の更新」で回す。
   - 仕様の決定が無ければ、止まらずに段 2 へ進む。
   - 選択肢には、本文から決められないなら**「定めない（実装に任せ、テストの期待にしない）」も入れる**。それが選ばれても決定として記録する
     （記録が無いと、別のケースで同じ問いがまた出る）。
   - **段 2 以降のレビューで新しい仕様の決定が出たら**（レビュー役の指摘「仕様に無い期待」から出た問いも含む）、決定のレポートに追記して
     （決定のレポートが無いケースなら作る）、同じように対話で聞く。影響するケースは期待を推測で書かずに保留し、
     それ以外は進めてよい。**段 4 の承認（Green のコミット）の前に、人の判断を待つ。**
4. **段 2（Red）**：実装役にテストを書かせ、レビュー役に渡す（往復は 2 と同じ）。承認されたら、**司令役がコミットする**（テスト仕様とテスト）。
5. **段 3・段 4（Green）**：実装役に計画と実装をさせ、レビュー役に渡す。承認されたら、司令役がコミットして push する。
6. **終わり**：人に、短い完了の報告（作った範囲・テストの件数・コミット・実装役とレビュー役のモデル ID・段ごとの指摘の数とレビュー役でだけ見つかった数）と、
   目で見る確認の頼み（任意）を返す。

## 人に上げて止まるとき
- 仕様の決定の判断（上の 3。対話で聞く。段 2 以降に出た決定は、保留して進め、段 4 の承認の前に判断を待つ）
- 決定記録の案を書いた後のコミット（人が行う。待つ間も段 2 以降は進めてよい）
- 管理者の権限が要る操作（例：SQL Server のサービスが止まっている）
- 3 往復で承認されない差し戻し
- push が資格情報で失敗したとき（下の「コミット」）
- 検出器（commit-msg フック）がコミットを止めたが、`TESTING.md` 3・4 から正当な理由を書けないとき

## 仕様の更新
人から「仕様が <版> に更新された」と言われたら、同じ実装役・レビュー役で `TESTING.md` 4 節を段 1 から回す（本文と決定記録を合わせて差分を見る）。
規約（[フレームワーク毎の共通仕様](../spec/test1-framework.md) など）が更新されたと言われたときも、同じく回す（規約で決まったことを、テスト仕様の決定・保留からも探す）。

## コミット
- 司令役がコミットする（この手順書が `AGENTS.md`「Git 操作は行わない」の「指示」にあたる。実装役・レビュー役はコミットしない）。
  メッセージはトレーラーの決まり（`AGENTS.md`・`TESTING.md` 3・4）に従う。
  段 2・段 4 のコミットには、確かめ方のトレーラーを付ける：`Tested-with:`（その段で流したテストの種類。段 2 は Red を確かめた種類）と、
  `Reviewed-with: opentouryo-test-reviewer (<レビュー役のモデル ID>)`（その段を承認したレビュー役）。
- **最初のコミットの前に 1 回だけ、コミットと push のアカウントを人に聞く**（質問の道具で。以後このセッションではそれを使い、聞き直さない）。
  - コミットの作成者：`git config user.name`・`user.email` を示し、このままでよいかを聞く。
  - push：`gh auth status` に出るアカウントを選択肢に（間引かない）、「gh を使わない（push は人が行う）」も加えて聞く。
- push は入力を待たせない設定で行う（`GIT_TERMINAL_PROMPT=0`・`GCM_INTERACTIVE=never`。資格情報の画面を待って止まらないため）。
  gh のアカウントが選ばれていたら、その資格情報で push する：
  `GH_TOKEN=$(gh auth token --user <アカウント>) git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push`
  （`credential.helper=` で既定の資格情報の仕組みを外し、gh だけを使う）。
  gh を使わない、または失敗したら、人に `! git push` を頼んで止まる。
- **メッセージの文面に仮置き（「N 往復目」など）を残さない。** 決まっていない値があるなら、決まってから文面を出す（人が文案をそのまま使ってコミットすることがある）。
- **コミットの後に amend しない。** 人がコミット・push を代わりにしたかもしれないので、続ける前に `git fetch` と `git status -sb` で確かめる。
  文面の誤りは、次のコミットの本文に書いて正す（push 済みのコミットを書き換えると、履歴が分かれる）。
- Red（段 2）と Green（段 4）は別のコミットにする。段 4 の後にテストを直す必要が出たら、理由を書いた別のコミットにする（期待を変えるならトレーラー）。
