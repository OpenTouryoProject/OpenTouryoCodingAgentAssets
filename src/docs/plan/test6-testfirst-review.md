# テスト先行・テスト6：レビューの観点

**レビュー役が使う**（司令役が渡す）。段 1（テスト仕様）・段 2（Red）・段 4（Green）を承認する前に、ここと突き合わせる。
**実装役には読ませない**（読むと、仕様からテストを起こす力を確かめられない）。

## どの対象にも共通

段 1 で次があれば差し戻す。

- 根拠の ID が無いケース、仕様に無い期待値（今のコードや推測から書いたもの）
- どの実装でも通る期待（仕様の別の規則で起こりえない状況の期待）
- 期待を実装と同じ式（SQL）で作っている（テストが入れた値から C# で作る）
- 並びを C# の比較（`string.Compare`・`OrderBy`）で確かめている（DB の照合順序と一致しない。テストが入れた行どうしの前後関係で確かめ、2 つ目の並びのキーも確かめる）
- Northwind の既存の行の件数・名前に頼る（テスト用の顧客などで絞る）
- E2E で、B層で確かめられること（並び・金額・抽出条件）を網羅している
- 仕様の決定と実装の決定の取り違え（`TESTING.md` 5。例：hidden か Session かは実装の決定）

段 2：

- 期待（`Assert`・E2E の `Expect`）で落ちている。`UOC_` が無いことの `ArgumentException`、起動・ログイン・接続の失敗、`ClickAsync` のタイムアウトではない
  （E2E は、まだ無いボタンを押す前に `Expect(...).ToBeEnabledAsync()` を置く）
- 最初から通ったケースは、実装を 1 か所ずつ壊して落ちた記録があり、**どのケースもいずれかの壊し方で落ちている**
  （例：最終ページの件数・総件数だけでは、`PageNo` を無視する壊し方で落ちない。そのページの `OrderID` も確かめる）
- テストのプロジェクトの形がスキルのとおり（`<Web>.Tests`・`<Web>.E2ETests`、NUnit、`[Basis]`、`[TearDown]` での後始末）。`[Basis]` がテスト仕様と一致
- テストが入れたデータ・アプリのプロセスが、実行の後に残っていない
- 固定の時間を待っていない（`Task.Delay`）

段 4：

- 全件合格（`dotnet test <sln>` を `-m:1` なしで。並行して動く B層と E2E のデータが干渉しない）
- テストのプロジェクトが段 2 のコミットから変わっていない（`git diff`）
- 実装が計画と仕様（決定記録を含む）に沿っている
- 共通のレイアウト（`_Layout.cshtml`・Master Page など）を変えたなら、ログイン後の既存の画面が崩れていない
